# OF-119 · BUG: Timestamps lose their UTC "Z" after a round-trip to the database

| Type | Priority | Points | Reporter | Labels |
|------|----------|--------|----------|--------|
| Bug 🐞 | Low | 2 | Web team | `dates`, `ef-core`, `sqlite` |

## Description
`POST /api/orders` returns `"createdAtUtc": "2026-10-09T17:40:43.731292Z"` ✅, but
`GET /api/orders/{id}` for the same order returns `"2026-10-09T17:40:43.731292"` (no `Z`).
The browser treats the second one as *local time*, so users in Chicago see orders placed 5 hours in the future.

## Acceptance Criteria
- [ ] All `DateTime` values read from the database come back as `DateTimeKind.Utc`
- [ ] The fix is global (one place), not sprinkled per entity
- [ ] Discuss in PR: would `DateTimeOffset` have avoided this? What do *you* recommend for new code?

<details><summary>Hints</summary>

SQLite has no native datetime type. Look up EF Core **value converters** and `ConfigureConventions` in `DbContext`.
</details>
